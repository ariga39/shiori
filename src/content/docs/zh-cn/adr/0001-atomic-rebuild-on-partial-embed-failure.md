- **日期：** 2026-08-03

## 背景（Context）

每个 session id 的存储使用先删后插策略：先移除既有块，再整批重插。在本决策之前，嵌入失败的保底逻辑为：

- 若**全部**嵌入失败 → 直接提交返回，不触发 DELETE，已有数据得以保留；
- 若**部分**失败 → DELETE 已执行，失败块被跳过不插入，形成部分重建，由 `partial=True` 记录。

问题：这是记忆系统，丢块等于丢记忆。部分失败后旧块已被销毁但新块未完整补回，该 session 的块数少于应有值，且要等后续 mtime/size 变化或强制全量重跑才能补全。

## 决策（Decision）

选择方案 1：原子全量重建。嵌入在删除前准备完成，删除与插入保持事务原子性。

1. 先对该 batch 的**所有** chunks 计算 embedding；若任何一块嵌入失败则**整体不写**（不 DELETE、不 INSERT），保留既有数据并标记 `partial=True` 等待重试。
2. 仅当整批嵌入全部成功时才执行 `DELETE` + 全量 `INSERT`，形成「要么全量替换、要么完全不变」的原子语义。

受保护摄取路径上的既有 advisory lock 防止嵌入阶段出现另一实例并发写入的竞态。

## 备选方案（Alternatives）

- **方案 2：repair 标记。** 新增标记列并扩展断点逻辑以记录并补齐缺失块。可精确修复，但需新增数据库列并改动断点语义，且仍无法消除「DELETE 与 INSERT 之间的失败窗口」。
- **方案 3：仅文档化。** 只在文档里写明该限制。只是把数据丢失写清楚，问题仍在，不采用。

## 后果（Consequences）

**正向：**

- 消除部分重建导致的数据丢失；记忆系统不允许丢块。
- write-ahead 顺序使原子性天然成立，比方案 2 的标记/断点机制简单可靠。

**负向 / 代价：**

- 单批文件很多时（如首次全量、强制全量重跑），一次性嵌入全部 chunks 的等待时间会高于「边嵌入边写」，且需在内存中持有整批向量。
- 失败即整批不写，重试粒度从「单块」放大到「整批」；若个别坏文本持续嵌入失败，会阻塞该 session 的更新直到该块被排除或修复。

## 当前实现（Current implementation）

write-ahead 原子全量重建已在 sessions 与 Discord 摄取路径的 `store_chunks` 中实现，Hermes 摄取路径复用 sessions 的切块/嵌入/存储路径，因此三个数据源执行同一契约：

- 在任何删除前先校验整批 embedding；
- 任一 embedding 缺失或失败 → 不 DELETE、不 INSERT，调用方记录 `partial=True`；
- 整批成功 → 执行 DELETE + 全量 INSERT，调用方记录 `partial=False`；
- 任一 INSERT 失败 → 整批 `rollback()`（撤销 DELETE+INSERT），调用方记录 `partial=True`。

`partial=True` 结果以 size 为 0 写入断点，使该文件在下次运行时被重试，而不是被当作已完整处理。advisory lock 串行化同一受保护摄取路径的并发运行。
